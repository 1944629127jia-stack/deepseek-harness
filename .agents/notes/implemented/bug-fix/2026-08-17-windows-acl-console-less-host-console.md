# Agent Note: The windows-acl backend requires a console on console-less hosts

Status: implemented

English | [中文](2026-08-17-windows-acl-console-less-host-console.zh.md)

## Problem

In the packaged desktop shell (Electron GUI — no console anywhere in its process tree), every confined shell command died with exit code 3221225794 (`0xC0000142`, `STATUS_DLL_INIT_FAILED`) and zero output; the same command unconfined (`danger-full-access`) ran fine. Every standalone replay of the failing chain — same binary, same runner argv, same workspace, same SID pair, same environment block, same piped stdio shape, an identical parent-token group list — succeeded outside the live app, so the trigger was pinned down inside the app's own process context by instrumenting the installed runner as a debug loop. Loader-snaps output from the dying child showed process initialization failing inside KernelBase's `DLL_PROCESS_ATTACH` after only ntdll/kernel32/KernelBase had mapped. A creation-flag probe matrix then run inside the app's runtime settled the shape: every console-touching variant (no flags, `CREATE_NO_WINDOW`, `CREATE_NEW_CONSOLE`) died with `0xC0000142`; `DETACHED_PROCESS` started but PowerShell exited vacuously (no command run, exit 0, no output — a false positive); and a runner that first allocated a console for itself produced a confined child that attached and ran with real output. The restriction scheme's verified design — children share the host console ([design note](../feature/2026-08-08-windows-acl-restricted-token-sandbox.md)) — silently assumed the host has one; the desktop shell is the first console-less host.

The host-side accommodation alone did not close it: confined commands still died in the packaged shell, intermittently. Live instrumentation of the installed runner showed why: the desktop shell launches the runner through its own Electron binary under `ELECTRON_RUN_AS_NODE`, and a GUI-subsystem image never inherits the parent's console at creation, so the runner started with `GetConsoleWindow() == NULL` even though its parent (the backend) owned the hidden console; an explicit `AttachConsole(ATTACH_PARENT_PROCESS)` in the runner attached immediately and the confined command ran with real output. The intermittency is the confined child's fallback: with no console to inherit it must create one during process initialization, and that creation is fatal (`0xC0000142`) in the desktop shell's session state but succeeds from terminal-launched standalone replays — which is also why every offline replay of the chain looked healthy.

## Decision

The seam gives a console-less host ONE hidden console for its lifetime. `ensureHostConsole` (`sandbox-windows-acl/src/console.ts`) allocates a console only when the process has none (`GetConsoleWindow`) and immediately hides it (`ShowWindow` `SW_HIDE`); `dsh-sandbox-local` applies it before every windows-acl wrap (`windowsAclRunnerArgv`), win32-only and injectable as `internals.ensureConsole` for tests. Confined children then inherit the host's console attachment — exactly the shape the CLI verification pins. The accommodation is best-effort by design: an `AllocConsole` refusal leaves the pre-existing behavior rather than breaking hosts where the no-console path happens to work, because the failure is not universal to console-less hosts. The runner completes the chain from the other side. `attachParentConsole` (same module) attaches a console-less runner to its parent's console (`AttachConsole(ATTACH_PARENT_PROCESS)`); the runner calls it at startup, a no-op for console-subsystem images (plain node) that already inherited the attachment. It deliberately attaches rather than allocates: the host's hidden console already exists, so no new window appears and its lifetime stays with the host. Same best-effort stance: an attach refusal (parent truly has no console) leaves the pre-existing behavior. Coverage: `console.spec.ts` pins all four `ensureHostConsole` branches and all three `attachParentConsole` branches against stub bindings; `sandbox-local`'s `local.spec.ts` pins that every windows-acl wrap applies the hook; a runner e2e reproduces the console-less host from any terminal (a wrapper entry calls `FreeConsole` before loading the runner, then applies the accommodation) and asserts the confined PowerShell both survives AND emits real output — the assertion that rules out the vacuous-`DETACHED_PROCESS` false positive. The packaged-shell half is pinned by the live instrumentation record above (runner starts console-less, attach succeeds, confined output flows).

## Alternatives considered

- **`DETACHED_PROCESS` children on console-less hosts.** Rejected: the child starts but CUI tools run no command (PowerShell exits 0 with no output), verified in the desktop shell and in a local harness — an exit-0 silent no-op, strictly worse than a loud failure.
- **`CREATE_NO_WINDOW` / `CREATE_NEW_CONSOLE`.** Already documented as dying under the restriction; re-verified dying in the desktop shell's probe matrix.
- **Allocating the console inside the per-command runner.** Rejected: a console dies with its last attached process, so a per-command allocation would flash a console window per command; the console must belong to the long-lived provider process. The runner instead ATTACHES to that existing host console (`attachParentConsole`) — no new window, no lifetime change — which is the complement that makes the host's console reachable from a GUI-subsystem runner image.
- **Fixing the console-creation failure itself.** Out of reach: the failure sits inside KernelBase's console initialization under `WRITE_RESTRICTED` on this host shape, and the POC's documented SID attempts (`S-1-2-1`) already failed; inheriting an existing console is the verified working path.

## Consequences

- Packaged desktop shell: confined pwsh commands run with real output; one hidden console (one conhost.exe) per runtime lifetime, established at the first confined wrap, and reached from every GUI-subsystem runner via the parent-console attach.
- Non-Windows platforms untouched (both calls are win32-gated); hosts and runner images that already own a console take a no-op fast path.
- `win32-abi.ts`'s console notes and both package READMEs now state the host-console requirement and the runner's parent-console attach; the design note's console clause cross-links this note.
